CI/CD & deployment

Deployment pipelines, environment configuration and release process — so shipping to production is a routine operation rather than an event requiring everyone to be available.

DockerGitHub ActionsNginxGitLet's EncryptVPS hosting

The situation

Deployment is often manual, undocumented and performed by whoever built the system. Releases happen late at night, rollback means restoring a database dump, and staging either does not exist or has drifted far from production.

How I approach it

I automate the path from commit to production and hold environments at parity, so what was verified in staging is what reaches users. Rollback is designed in from the outset rather than improvised under pressure.

In practice

What the work covers.

Scope of work

  • CI/CD pipeline configuration from repository through to production release
  • Environment provisioning with parity between staging and production
  • Containerisation and reproducible build configuration
  • Domain, DNS, TLS certificate and reverse-proxy setup
  • Zero-downtime deployment with a defined rollback procedure
  • Build and deployment monitoring with failure alerting

What it delivers

  • Releases performed during working hours without ceremony
  • Rollback measured in minutes, not in restore windows
  • Staging behaviour that reliably predicts production behaviour
  • Deployment capability that is not held by a single engineer
